# PROJECT_RULES.md

이 문서는 HOMEPAGE 프로젝트의 고유 개발 규칙, QA 규칙, 보안 규칙, DB 규칙을 정의한다.

## 프로젝트 구조

루트 기준 주요 영역:

- `frontend/`: React/Vite 기반 사용자, 관리자, 스튜디오 화면
- `backend/`: Node.js/Express 기반 API 서버
- `deploy/`: 배포 관련 설정과 스크립트
- `docs/`: 추가 문서가 필요한 경우 사용하는 문서 폴더
- `AGENTS.md`: AI 최상위 작업 지침
- `docs/WORKFLOW.md`: 자동 테스트/정리/리팩토링 실행 흐름
- `docs/PROJECT_RULES.md`: 프로젝트 고유 규칙
- `docs/TASK.md`: 현재 작업 상태
- `docs/QA_DEPLOY_CHECKLIST.md`: 배포 전 체크리스트
- `README.md`: 프로젝트 소개와 실행 방법

## frontend 역할

프론트엔드는 사용자가 직접 보는 화면과 관리자가 운영하는 화면을 담당한다.

기준:

- React 18과 Vite 기준으로 작성한다.
- React Router 라우팅 구조를 유지한다.
- 사용자 화면과 관리자 화면의 역할을 혼동하지 않는다.
- 교육회원 관리와 스튜디오회원 관리는 데이터 의미를 분리한다.
- UI에 보이는 버튼, 링크, 입력창은 실제 기능과 연결한다.
- 모바일과 데스크톱 모두에서 사용 가능해야 한다.

## backend 역할

백엔드는 인증, 권한, DB 처리, 파일 업로드, 결제/환불, 예약, 알림 준비 구조를 담당한다.

기준:

- Node.js와 Express 기준으로 작성한다.
- 기능별 feature 구조를 우선한다.
- API 응답 형식을 일관되게 유지한다.
- 권한 검사는 프론트엔드가 아니라 백엔드에서 최종 보장한다.
- 결제, 환불, 예약, 수강권 차감은 DB 정합성을 우선한다.
- 민감정보는 로그에 출력하지 않는다.

확인 대상:

- nginx
- PM2
- `/api` 프록시
- `/uploads` 정적 경로
- HTTPS
- CORS
- 환경변수
- 이미지/영상 저장 경로

## Role 기준

권한은 화면, 메뉴, 버튼, API, DB 접근에 모두 영향을 준다.

기본 Role:

- Guest: 비회원
- Member: 일반회원
- Education Member: 교육영상을 구매하거나 선물받은 회원
- Studio Member: 스튜디오 수강권 또는 스튜디오 프로필이 있는 회원
- Admin: 관리자

관리자 기능은 Admin만 접근 가능해야 한다.
일반 사용자가 관리자 URL이나 관리자 API를 직접 호출하면 401 또는 403으로 차단해야 한다.

## 사용자/관리자 버튼 테스트 원칙

화면에 보이는 버튼만 테스트하지 않는다.

다음을 모두 확인한다.

- 비회원에게 보이는 버튼
- 일반 회원에게 보이는 버튼
- 교육회원에게 보이는 버튼
- 관리자에게 보이는 버튼
- 조건에 따라 나타나는 버튼
- 데이터 상태에 따라 나타나는 버튼
- 예약 가능 상태의 버튼
- 예약 완료 상태의 버튼
- 구매 전 버튼
- 구매 후 버튼
- 환불 가능 버튼
- 환불 완료 후 버튼
- 모바일에서만 보이는 버튼
- 데스크톱에서만 보이는 버튼
- 비활성화 상태의 버튼

각 버튼은 클릭만 확인하지 않고 다음까지 확인한다.

- 클릭 동작
- API 호출
- DB 반영
- 화면 반영
- 권한 검증
- 새로고침 후 유지
- Console Error
- Network Error

- 구매 전: 구매하기

- 관리자: 등록, 수정, 삭제
- 권한 없음: 숨김 또는 비활성화

## API 규칙

API는 다음 기준을 만족해야 한다.

- URL과 Method가 명확해야 한다.
- 인증이 필요한 API는 토큰을 확인한다.
- 관리자 API는 관리자 권한을 확인한다.
- 요청 값 검증을 수행한다.
- 실패 응답은 사용자가 이해할 수 있는 메시지로 반환한다.
- 401, 403, 404, 409, 422, 500 처리를 구분한다.
- 동일 기능의 중복 API wrapper는 정리 후보로 분류한다.

## Database 규칙

DB 변경은 화면, API, 실제 DB 결과가 모두 일치해야 완료다.

확인 기준:

- 생성 후 조회 가능
- 수정 후 값 반영
- 삭제 또는 상태 변경 후 화면 반영
- 외래키 관계 유지
- 중복 데이터 방지
- 예약, 수강권, 결제, 환불은 트랜잭션 고려
- 테이블과 컬럼 의미는 비개발자도 이해할 수 있게 주석 또는 문서로 설명

DB 스키마 변경이 필요한 경우 자동 진행하지 말고 사용자 승인을 받는다.

## 보안 규칙

다음 항목은 반드시 확인한다.

- 관리자 URL 직접 접근 차단
- 관리자 API 직접 호출 차단
- 타인 데이터 접근 차단
- XSS 입력 처리
- SQL Injection 방어
- 파일 업로드 확장자와 MIME 검증
- 민감정보 로그 출력 금지
- 환경변수 노출 금지
- CORS 허용 도메인 확인

비밀번호, API Key, Secret Key는 문서와 로그에서 `[REDACTED]`로 표시한다.
`.env` 파일 내용은 출력하지 않는다.
API Key, Secret Key, Token, JWT Secret, SMTP, SMS, Payment Key는 원문을 출력하지 않는다.
민감정보가 의심되면 값을 출력하지 말고 “민감정보 존재 가능성”으로만 보고한다.
`frontend/.env.example`에는 실제 값이 아닌 변수명과 예시 설명만 포함해야 한다.

## 보안 기준

보안 세부 기준은 `docs/SECURITY_HARDENING.md`를 따른다.

프로젝트의 모든 기능은 다음을 만족해야 한다.

- 프론트엔드 권한 표시와 백엔드 권한 검증이 모두 존재해야 한다.
- 관리자 API는 서버에서 반드시 관리자 권한을 확인해야 한다.
- 사용자 데이터 API는 반드시 소유권을 확인해야 한다.
- API 응답은 필요한 데이터만 반환해야 한다.
- 개인정보는 로그, Console, 에러 메시지에 노출되면 안 된다.
- 파일 업로드는 확장자, MIME type, 크기, 저장 경로를 검증해야 한다.
- 환경변수와 비밀키는 프론트엔드 번들에 포함되면 안 된다.

## 브라우저 테스트 보고 규칙

실제 브라우저를 띄워 확인하지 못한 경우에는 UI와 Console, Network 상태를 확인했다고 말하지 않는다.

- 브라우저 직접 확인을 하지 못한 경우 “브라우저 직접 확인 불가”라고 보고한다.
- 실제 화면 확인 없이 UI 정상이라고 단정하지 않는다.
- Console Error와 Network Error를 확인하지 못했다면 “미확인”으로 표시한다.
- 테스트하지 않은 항목은 완료가 아니라 “미확인”으로 표시한다.

## 이미지/영상 업로드 규칙

이미지:

- JPG, PNG 허용
- 허용하지 않는 확장자 차단
- 용량 제한 안내
- 업로드 후 미리보기
- 새로고침 후 경로 유지
- 배포 환경 경로 확인

업로드 이미지 자동 최적화:

- 업로드된 이미지는 서버에서 긴 변 1920px 이하로 줄이고 webp로 변환해 저장한다 (`backend/src/shared/media/image-optimizer.js`).
- 적용 지점: 커뮤니티 자산, 스튜디오 공지 이미지, 아카데미 이미지.
- **검증 순서를 바꾸지 않는다.** 확장자·매직 바이트 검증과 용량 제한은 반드시 원본에 먼저 적용하고, 그 뒤에만 변환한다. 변환을 먼저 하면 매직 바이트 검사가 무의미해지고 압축으로 용량 제한을 우회할 수 있다.
- 최적화 실패는 업로드를 막지 않는다. 변환에 실패하면 원본을 그대로 저장한다.
- 변환 결과가 원본보다 크면 원본을 유지한다.
- GIF는 애니메이션이 사라지므로 변환하지 않는다.
- EXIF 회전 정보를 반영한다. 반영하지 않고 리사이즈하면 세로 사진이 눕는다.
- 인쇄용 원본처럼 고해상도가 필요한 자산은 이 경로로 올리지 않고 별도로 관리한다.


영상:

- MP4, MOV 허용
- 용량 제한 안내
- 업로드 실패 원인 표시
- 영상 길이 자동 표시
- 파일 용량 자동 표시
- 썸네일 미등록 시 기본 썸네일 또는 첫 프레임 사용
- 권한 없는 직접 재생 차단

- 사용되지 않는 import
- 사용되지 않는 변수

- 호출되지 않는 컴포넌트

사용 여부가 불확실하면 삭제하지 말고 “삭제 후보”로 보고한다.

## 리팩토링 규칙

리팩토링은 기능 변경이 아니다.

원칙:

- 기존 UI를 임의로 바꾸지 않는다.
- 기능 동작을 변경하지 않는다.
- 기존 API 응답 구조를 임의로 바꾸지 않는다.
- 작은 단위로 분리한다.
- 한 번에 여러 영역을 대규모로 바꾸지 않는다.
- 분리 후 즉시 빌드와 관련 기능을 테스트한다.
- 중복 Header, Footer, Sidebar, Button, Modal, Table, Card, Pagination, Search/Filter, Upload UI, API 호출 로직, 권한 체크 로직은 공통화 후보로 본다.
- 공통 컴포넌트로 분리한 경우 기존 페이지에서 모두 정상 호출되는지 확인한다.
- 공통화 후 기존 화면과 기능이 동일하게 동작하는지 확인한다.
- 리팩토링 전후 빌드와 주요 기능 회귀 테스트를 수행한다.
- 영향 범위가 크면 자동 진행하지 말고 사용자에게 보고한다.

## 한글 주석 규칙

비개발자도 이해해야 하는 복잡한 로직에는 한글 주석을 남긴다.

대상:

- 인증/권한
- 예약
- 수강권
- 결제
- 환불
- 영상 권한
- 파일 업로드
- 스케줄러
- DB 트랜잭션
- 복잡한 조건문

주석은 코드가 무엇을 하는지보다 왜 그렇게 처리하는지를 설명한다.

## Git 규칙

- 작업 전 `git status --short`를 확인한다.
- 사용자 변경을 되돌리지 않는다.
- 사용자가 요청하지 않으면 `git add`, commit, push를 하지 않는다.
- 커밋이 필요한 경우 변경 범위와 포함 파일을 먼저 확인한다.
- 업로드 파일, 덤프 파일, 민감정보 파일은 커밋하지 않는다.

## 외부 부작용 차단 규칙

테스트와 개발 작업에서는 실제 사용자에게 영향을 줄 수 있는 외부 호출을 기본 차단한다.

- 이메일, SMS, 카카오 알림톡, FCM Push는 명시적인 허용 플래그가 없으면 실제 발송하지 않는다.
- PortOne 결제 조회와 환불 호출은 `ALLOW_EXTERNAL_PAYMENT_CALLS=true`가 아니면 실제 외부 API를 호출하지 않는다.
- `TEST_SAFE_MODE=true`에서는 외부 발송과 결제/환불 호출을 항상 차단한다.
- 서버 시작 시 자동 스케줄러는 기본 비활성화한다.
- 운영 환경에서 외부 연동을 켜야 하는 경우 테스트 DB/테스트 키와 운영 DB/운영 키를 명확히 분리한 뒤 진행한다.
- 테스트 결과 보고서에는 실제 발송, 실제 결제/환불, 실제 DB 변경을 수행했는지 여부를 명확히 기록한다.
