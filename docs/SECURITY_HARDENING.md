## 인증 보안

- 로그인 실패 시 명확하지만 과도한 정보를 주지 않는다.
- 존재하지 않는 계정과 비밀번호 오류 메시지는 공격자가 계정 존재 여부를 추측하지 못하도록 처리한다.
- 비밀번호는 평문 저장을 금지한다.
- 비밀번호는 안전한 해시 알고리즘을 사용한다.
- JWT 또는 세션 만료 처리를 확인한다.
- 로그아웃 후 보호 페이지 접근을 차단한다.
- 토큰 변조 시 접근을 차단한다.
- 관리자 계정은 일반 사용자 계정과 권한이 명확히 분리되어야 한다.
- 관리자 계정에는 가능하면 2차 인증 또는 추가 보호를 검토한다.

## 권한 보안

- 권한 검사는 프론트엔드에서만 하면 안 된다.
- 모든 관리자 API는 백엔드에서 권한을 검증해야 한다.
- 모든 사용자 데이터 API는 요청자의 소유권을 검증해야 한다.
- URL 직접 접근으로 관리자 화면에 들어갈 수 없어야 한다.
- API 직접 호출로 관리자 기능을 사용할 수 없어야 한다.
- 다른 회원의 주문, 예약, 수강내역, 개인정보를 조회할 수 없어야 한다.
- ID 값만 바꿔 타인 데이터를 조회하는 IDOR/BOLA 취약점을 반드시 점검한다.

## 관리자 보안

- 관리자 URL 직접 접근을 차단한다.
- 관리자 API 직접 호출을 차단한다.
- 관리자 메뉴는 Role 기반으로 노출한다.
- 관리자 권한은 서버에서 검증한다.
- 관리자 작업 로그 기록을 검토한다.
- 매출, 환불, 회원정보 접근을 보호한다.
- 관리자 기능은 일반 회원 토큰으로 호출할 수 없어야 한다.
- 관리자 세션 만료 처리를 확인한다.

## 개인정보 보호

- 이름, 전화번호, 이메일, 주문내역, 예약내역, 결제정보 등 개인정보 노출 범위를 확인한다.
- API 응답에서 불필요한 개인정보를 제거한다.
- 관리자 화면 외 개인정보 과다 노출을 금지한다.
- 로그에 개인정보를 출력하지 않는다.
- 브라우저 Console에 개인정보를 출력하지 않는다.
- 에러 메시지에 DB 정보 또는 내부 경로를 출력하지 않는다.

## API 보안

- 모든 API의 인증 필요 여부를 확인한다.
- 모든 API의 권한 필요 여부를 확인한다.
- Role별 접근 제어를 확인한다.
- 요청 Body는 화이트리스트 방식으로 검증한다.
- Mass Assignment를 방지한다.
- Pagination 제한을 둔다.
- 과도한 데이터 반환을 방지한다.
- 민감 필드는 응답에서 제외한다.
- Error Response에 내부 정보를 노출하지 않는다.
- API Rate Limit을 검토한다.
- 관리자 API는 일반 사용자 접근을 차단한다.

## Database 보안

- DB 계정은 최소 권한 원칙을 적용한다.
- 운영 DB 계정과 개발 DB 계정을 분리한다.
- DB 연결 정보는 환경변수로 관리한다.
- DB 연결 정보는 Git 커밋을 금지한다.
- SQL 사용 시 Parameterized Query를 사용한다.
- NoSQL 사용 시 사용자 입력 기반 조건 주입을 방지한다.
- 삭제 작업은 Soft Delete 또는 이력 보존 정책을 검토한다.
- 관리자/회원 데이터 접근 권한을 분리한다.
- 백업/복구 정책을 확인한다.
- DB 에러 메시지를 사용자에게 직접 노출하지 않는다.

## 파일 업로드 보안

- 확장자를 검증한다.
- MIME type을 검증한다.
- 파일 크기를 제한한다.
- 파일명은 랜덤화 또는 UUID 처리한다.
- 경로 탐색 공격을 방지한다.
- 실행 가능한 파일을 차단한다.
- SVG, HTML, JS, PHP, JSP, EXE 등 위험 파일을 차단한다.
- 업로드 폴더에서 스크립트 실행을 금지한다.
- 업로드 파일 직접 접근 경로를 점검한다.
- 사용자별 업로드 권한을 확인한다.

## 이미지/영상 업로드 보안

- 이미지 허용 확장자를 제한한다.
- 영상 허용 확장자를 제한한다.
- 대용량 업로드를 제한한다.
- 업로드 중 실패 처리를 확인한다.
- 업로드 후 DB URL을 검증한다.
- 업로드 파일 삭제 시 실제 파일과 DB 정합성을 확인한다.
- `/uploads` 경로 노출 범위를 확인한다.
- 배포 환경에서 업로드 파일 유지 여부를 확인한다.

## CSRF 방어

- 쿠키 기반 인증을 사용하는 경우 CSRF 토큰 또는 SameSite 정책을 확인한다.
- 상태 변경 API는 인증/권한 검증이 필요하다.
- CORS와 credentials 설정을 확인한다.

## CORS 보안

- 운영 환경에서 `*` 허용을 금지한다.
- 허용 Origin을 명확히 제한한다.
- credentials 사용 시 Origin 제한은 필수다.
- 개발/운영 CORS 설정을 분리한다.
- 관리자 API CORS 노출을 점검한다.

## Rate Limit / Brute Force 방어

- 로그인 API Rate Limit을 확인한다.
- 관리자 로그인 Rate Limit을 확인한다.
- 비밀번호 재시도 제한을 검토한다.
- 동일 IP 과도 요청을 제한한다.
- 동일 계정 과도 로그인 시도를 제한한다.
- 파일 업로드 Rate Limit을 검토한다.
- 예약/주문 생성 API Rate Limit을 검토한다.
- 문의 작성 Rate Limit을 검토한다.
- 429 응답 처리를 확인한다.
- 필요 시 CAPTCHA 또는 추가 인증을 검토한다.

## 세션 / JWT 보안

## 외부 발송/결제/스케줄러 보안 기준

외부 서비스 호출은 테스트 중 가장 큰 부작용을 만들 수 있으므로 기본 차단을 원칙으로 한다.

- 실제 이메일 발송은 `ALLOW_EXTERNAL_EMAIL_SEND=true`인 경우에만 허용한다.
- 실제 SMS 발송은 `ALLOW_EXTERNAL_SMS_SEND=true`인 경우에만 허용한다.
- 실제 카카오 알림톡 발송은 `ALLOW_EXTERNAL_KAKAO_SEND=true`인 경우에만 허용한다.
- 실제 FCM Push 발송은 `ALLOW_EXTERNAL_PUSH_SEND=true`인 경우에만 허용한다.
- 실제 PortOne 결제 조회/환불 호출은 `ALLOW_EXTERNAL_PAYMENT_CALLS=true`인 경우에만 허용한다.
- `TEST_SAFE_MODE=true`이면 위 외부 호출은 플래그 값과 관계없이 차단한다.
- 아카데미 공개 예약 스케줄러는 `ACADEMY_PUBLISH_SCHEDULER_ENABLED=true`가 명시된 경우에만 실행한다.
- 외부 호출을 차단할 때 수신자 전화번호, 이메일, 토큰, 결제 키, API Key 원문을 로그에 출력하지 않는다.
- 운영 DB 또는 운영 외부 서비스 연결 가능성이 있으면 전체 테스트를 중단하고 사용자에게 보고한다.

## 테스트 DB 및 외부 서비스 보안 기준

전체 E2E 테스트는 테스트 전용 환경에서만 진행한다.

- 운영 DB에서 테스트 금지
- 운영 복제 DB에서 테스트 금지
- 실제 사용자 데이터가 있는 개발 DB에서 테스트 금지
- 운영 결제키로 테스트 금지
- 운영 SMTP/SMS/카카오/FCM 키로 테스트 금지
- 테스트 환경 파일에는 실제 secret 금지
- 테스트 데이터에는 `test`, `e2e`, `qa` 등 명확한 prefix 사용 권장
- 테스트 완료 후 생성 데이터와 업로드 파일을 정리할 수 있어야 한다.
- DB 변경 E2E는 테스트 전용 DB가 확인되고 `ALLOW_E2E_DATA_MUTATION=true`가 명시된 경우에만 허용한다.
- 외부 발송과 결제/환불은 mock, sandbox 또는 비활성화 상태에서만 테스트한다.
- 테스트 중 민감정보, 결제키, 외부 서비스 키, DB 비밀번호 원문을 로그나 보고서에 출력하지 않는다.

테스트 모드별 보안 기준:

- 비파괴 테스트 모드: `TEST_SAFE_MODE=true`, `ALLOW_E2E_DATA_MUTATION=false`
- 전체 E2E 테스트 모드: `TEST_SAFE_MODE=true`, `ALLOW_E2E_DATA_MUTATION=true`
- 전체 E2E 테스트 모드에서도 외부 이메일/SMS/카카오/FCM 발송은 차단한다.
- 전체 E2E 테스트 모드에서도 실제 결제/환불 외부 API 호출은 차단한다.
- 전체 E2E 테스트 모드에서도 scheduler는 비활성화한다.
- 전체 E2E 테스트 모드의 DB 쓰기는 테스트 전용 DB에서만 허용한다.
- 코드 구현이 위 정책과 다르거나 DB 쓰기 가드가 명확하지 않으면 전체 E2E를 실행하지 않고 정책 충돌로 보고한다.

## E2E DB 쓰기 보안 정책

- `TEST_SAFE_MODE=true`는 이메일, SMS, 카카오 알림톡, FCM, 결제/환불 외부 호출, 스케줄러 같은 외부 부작용을 차단하는 설정이다.
- `ALLOW_E2E_DATA_MUTATION=true`는 테스트 전용 DB에서만 DB 쓰기 E2E를 허용하는 설정이다.
- `NODE_ENV=production`에서는 `ALLOW_E2E_DATA_MUTATION=true`가 설정되어 있어도 코드에서 무시되어야 한다.
- DB 이름이 test/e2e/qa 성격으로 확인되지 않으면 DB 쓰기 E2E를 허용하지 않는다.
- 운영 DB 또는 실제 사용자 데이터가 있는 DB에서는 `ALLOW_E2E_DATA_MUTATION=true`를 설정하지 않는다.
- 전체 E2E 전에는 `env.isTestDatabase`와 `env.allowE2eDataMutation`의 effective 값을 기준으로 진행 가능 여부를 판단한다.

## 테스트 환경 보안 추가 기준

- `TEST_SAFE_MODE=true`는 외부 부작용 차단용이며, DB 쓰기 허용 여부와 분리해서 판단한다.
- `ALLOW_E2E_DATA_MUTATION=true`는 테스트 전용 DB에서만 허용한다.
- production에서는 `ALLOW_E2E_DATA_MUTATION=true`가 설정되어도 무시되어야 한다.
- DB 이름이 `test`, `e2e`, `qa`, `local_test`, `homepage_test` 성격으로 보이지 않으면 DB 쓰기 E2E를 허용하지 않는다.
- 업로드 테스트는 `UPLOAD_ROOT=uploads-test` 같은 격리된 경로에서만 진행한다.
- 실제 운영 업로드 폴더, 운영 DB, 운영 외부 발송 키, 운영 결제 키를 E2E에서 사용하지 않는다.
- Playwright smoke 테스트는 base URL이 없으면 skip되며, 서버를 자동으로 시작하지 않는다.
- 테스트 보고서에는 확인하지 않은 항목을 반드시 `미확인`으로 표기한다.

## 환불/결제 테스트 보안 기준

- 현재 환불 스키마는 `refund_requests`와 `studio_pass_refunds`를 기준으로 한다.
- 테스트를 위해 단일 `refunds` 테이블을 새로 만들지 않는다.
- `TEST_SAFE_MODE=true`에서는 실제 결제 조회, 실제 환불, 실제 외부 API 호출을 금지한다.
- `ALLOW_EXTERNAL_PAYMENT_CALLS=true`가 아니면 PortOne 결제/환불 API를 호출하지 않는다.
- E2E seed는 `homepage_test` 안의 `e2e_` prefix 데이터만 생성/갱신한다.
- 환불 테스트 결과 보고서에는 실제 외부 환불 호출 여부를 반드시 `없음` 또는 `차단됨`으로 명시한다.
