# WORKFLOW.md

이 문서는 Codex가 “테스트 진행해” 명령을 받았을 때 수행해야 하는 전체 자동 작업 흐름을 정의한다.

## 자동 실행 트리거

사용자가 아래 중 하나를 입력하면 전체 워크플로우를 시작한다.

- 테스트 진행해
- 전체 테스트 진행해
- 자동 테스트 진행해
- AGENTS.md 기준으로 전체 테스트 진행해

## 자율 진행 규칙

사용자가 “테스트 진행해”라고 입력하면 `docs/TASK.md`의 autonomous_mode 값과 관계없이 이번 실행에 한해 autonomous_mode를 true로 간주한다.

Codex는 각 단계의 완료 조건을 만족하면 다음 단계로 자동 진행할 수 있다.

단, 즉시 중단 조건에 해당하는 문제가 발견되면 자동 진행을 중단하고 사용자에게 보고한다.

각 단계가 끝날 때마다 내부적으로 진행 상황을 기록하되, 사용자 승인을 기다리지 않고 다음 단계로 넘어간다.

단, 위험 작업은 예외다.

## 즉시 중단 조건

아래 항목 중 하나라도 발생하면 자동 진행을 중단한다.

- DB 스키마 변경이 필요한 경우
- 실제 데이터 삭제가 필요한 경우
- 대규모 폴더 구조 변경이 필요한 경우
- 인증/권한 구조를 크게 변경해야 하는 경우
- 결제/환불 로직 변경이 필요한 경우
- 운영 배포 설정을 변경해야 하는 경우
- 환경변수 또는 비밀정보를 변경해야 하는 경우
- 실제 사용자 데이터에 영향을 줄 수 있는 경우
- 원인을 확신할 수 없는 경우
- 보안상 위험한 변경이 필요한 경우
- 민감정보 노출 가능성이 있는 경우
- 삭제하려는 코드가 실제로 사용 중인지 확신할 수 없는 경우
- 중복 컴포넌트 공통화 과정에서 기능 변경 가능성이 큰 경우
- 실제 사용자 데이터에 영향을 줄 수 있는 경우

## 기존 변경사항 보호 규칙

자동 워크플로우를 시작할 때는 반드시 `git status --short`를 확인하고 작업 전 상태로 기록한다.

작업 전부터 존재하던 변경사항은 사용자의 작업물일 수 있으므로 아래 원칙을 따른다.

- 기존 변경사항을 임의로 되돌리지 않는다.
- 기존 변경사항을 덮어쓰지 않는다.
- 사용자가 만든 변경사항인지 확실하지 않으면 수정하지 않는다.
- `.gitignore`, 환경변수 파일, 업로드 파일, 미추적 파일은 임의로 정리하지 않는다.
- 결과 보고서에 “작업 전 존재하던 변경사항”과 “이번 작업으로 변경한 파일”을 구분해서 보고한다.
- 작업 전 변경사항 목록은 고정된 예시가 아니라 작업 시작 시점의 `git status --short` 결과를 기준으로 기록한다.

## 브라우저 직접 확인 불가 시 보고 규칙

브라우저를 직접 띄워 확인하지 못한 경우에는 테스트했다고 단정하지 않는다.

- 브라우저 직접 확인을 하지 못한 경우 “브라우저 직접 확인 불가”라고 보고한다.
- 실제 화면 확인 없이 UI 정상이라고 단정하지 않는다.
- Console Error와 Network Error를 확인하지 못했다면 확인하지 못했다고 명시한다.
- 테스트하지 않은 항목은 “미확인”으로 표시한다.

## 테스트 수준 정의

테스트 결과는 확인한 범위에 따라 Level로 구분해서 보고한다.
높은 Level을 수행하지 못한 경우 낮은 Level 통과만으로 “운영 가능”이라고 단정하지 않는다.

### Level 1. 정적 분석

코드를 실행하지 않고 구조, import, 중복 코드, 권한 로직, 보안 위험, 죽은 코드 후보를 확인하는 수준이다.

### Level 2. 빌드/실행 검증

프론트엔드 빌드, 백엔드 실행, lint/test 스크립트, 서버 로그를 확인하는 수준이다.

### Level 3. API/DB 연동 검증

API 요청/응답, 상태코드, 권한, DB 저장/조회/수정/삭제 반영을 확인하는 수준이다.

### Level 4. 브라우저 E2E 검증

실제 브라우저 또는 Playwright/Cypress 등을 사용해 로그인, 버튼 클릭, 페이지 이동, 관리자/사용자 기능, Console Error, Network Error를 확인하는 수준이다.

### Level 5. Staging/배포 환경 검증

AWS, nginx, PM2, Vercel, Firebase, 도메인, SSL, /api, /uploads, 이미지/영상 경로, 운영 환경변수를 확인하는 수준이다.

### Level 6. 운영 안정성 검증

실제 사용자 베타 테스트, 모바일 실기기, 결제 샌드박스/운영 검수, 외부 보안 점검, 부하 테스트, 백업/복구, 롤백까지 확인하는 수준이다.

## 공통 단계 작성 형식

각 단계는 아래 형식으로 판단하고 보고한다.

### 목적

단계에서 확인하려는 목표를 명확히 한다.

### 수행 항목

실제로 실행하거나 확인한 항목을 적는다.

### 완료 조건

다음 단계로 넘어갈 수 있는 기준을 적는다.

### 실패 조건

작업을 실패로 판단하는 기준을 적는다.

### 실패 시 처리

원인 분석, 수정, 재테스트 또는 사용자 보고 중 어떤 처리를 했는지 적는다.

### 다음 단계 진행 조건

완료 조건 충족 또는 사용자 승인 여부를 적는다.

### 보고 내용

사용자에게 전달할 핵심 결과를 적는다.

## STEP 1. 프로젝트 분석

### 목적

현재 프로젝트 구조와 기술 스택, 기능 범위를 파악한다.

### 수행 항목

- 현재 경로 확인
- Git 상태 확인
- README.md 확인
- AGENTS.md 확인
- docs/WORKFLOW.md 확인
- docs/PROJECT_RULES.md 확인
- docs/TASK.md 확인
- docs/QA_DEPLOY_CHECKLIST.md 확인
- frontend 구조 확인
- backend 구조 확인
- deploy 구조 확인
- 주요 라우트와 API 구조 확인

### 완료 조건

프로젝트 구조, 기술 스택, 주요 기능, 현재 변경 상태를 설명할 수 있어야 한다.

### 실패 조건

루트 경로가 다르거나 필수 폴더를 찾을 수 없거나 문서가 깨져 읽히지 않는 경우 실패다.

### 실패 시 처리

원인을 보고하고, 경로 또는 문서 인코딩 문제를 먼저 해결한다.

### 다음 단계 진행 조건

프로젝트 구조와 현재 상태가 확인되면 STEP 2로 진행한다.

### 보고 내용

구조 요약, 기술 스택, 발견한 위험 요소를 보고한다.

## STEP 2. 실행 및 빌드 확인

### 목적

프론트엔드와 백엔드가 실행 및 빌드 가능한 상태인지 확인한다.

### 수행 항목

- frontend 의존성 상태 확인
- backend 의존성 상태 확인
- 프론트엔드 빌드 실행
- 백엔드 테스트 또는 문법 검사 실행
- 백엔드 서버 실행 가능 여부 확인
- `/api/health` 또는 주요 헬스체크 확인

### 완료 조건

프론트엔드 빌드가 성공하고 백엔드가 정상 실행 가능해야 한다.

### 실패 조건

빌드 실패, 서버 실행 실패, 의존성 누락, 반복 오류 로그가 있으면 실패다.

### 실패 시 처리

오류 로그를 근거로 원인을 수정하고 같은 명령을 다시 실행한다.

### 다음 단계 진행 조건

빌드와 실행 확인이 끝나면 STEP 3으로 진행한다.

### 보고 내용

실행한 명령, 성공 여부, 오류 수정 여부를 보고한다.

## STEP 3. 권한(Role) 분석

### 목적

비회원, 일반회원, 교육회원, 관리자 권한이 화면과 API에 올바르게 적용되는지 분석한다.

### 수행 항목

- 인증 흐름 확인
- 로그인 상태 저장 방식 확인
- 관리자 보호 라우트 확인
- 사용자 보호 라우트 확인
- 관리자 API 미들웨어 확인
- 일반 사용자 API 접근 제한 확인

### 완료 조건

Role별 접근 가능 화면, 차단 화면, API 권한 기준을 설명할 수 있어야 한다.

### 실패 조건

일반 사용자가 관리자 기능에 접근할 수 있거나 인증 없는 API 접근이 가능하면 실패다.

### 실패 시 처리

권한 검사 누락 위치를 수정하고 직접 URL 및 API 접근을 재테스트한다.

### 다음 단계 진행 조건

권한 구조가 확인되면 STEP 4로 진행한다.

### 보고 내용

## STEP 4. 화면(UI) 분석

사용자 화면과 관리자 화면의 UI 구조, 반응형, 조건부 요소를 분석한다.

- 관리자 대시보드 확인
- 교육관리 화면 확인
- 스튜디오 관리 화면 확인
- 예약 캘린더 확인
- 매출/회원/강사/수강권 화면 확인

### 완료 조건

주요 화면의 레이아웃, 버튼, 입력창, 테이블, 모달, 탭 상태를 파악해야 한다.

### 실패 조건

### 실패 시 처리

UI 문제를 원인별로 수정하고 동일 해상도에서 재확인한다.

- 분리 후 즉시 테스트한다.

## 테스트 안전 모드 실행 조건

전체 테스트를 실행하기 전에는 외부 부작용이 발생하지 않는지 먼저 확인한다.

- `TEST_SAFE_MODE=true` 사용을 권장한다.
- `DB_INIT_MODE=safe` 상태를 유지한다.
- `ACADEMY_PUBLISH_SCHEDULER_ENABLED=false` 상태를 유지한다.
- `ALLOW_EXTERNAL_EMAIL_SEND=false` 상태를 유지한다.
- `ALLOW_EXTERNAL_SMS_SEND=false` 상태를 유지한다.
- `ALLOW_EXTERNAL_KAKAO_SEND=false` 상태를 유지한다.
- `ALLOW_EXTERNAL_PUSH_SEND=false` 상태를 유지한다.
- `ALLOW_EXTERNAL_PAYMENT_CALLS=false` 상태를 유지한다.
- DB를 변경하는 E2E 테스트는 테스트 전용 DB가 확인되고 `ALLOW_E2E_DATA_MUTATION=true`가 명시된 경우에만 진행한다.
- 운영 DB, 운영 SMTP, 운영 SMS/카카오/FCM, 운영 결제/환불 키가 사용될 가능성이 있으면 전체 테스트를 중단하고 보고한다.

`TEST_SAFE_MODE=true`이면 다음 작업은 실행하지 않는다.

- 아카데미 공개 예약 스케줄러
- 실제 이메일 발송
- 실제 SMS 발송
- 실제 카카오 알림톡 발송
- 실제 FCM Push 발송
- 실제 PortOne 결제 조회/환불 호출
- 테스트 DB가 확인되지 않은 데이터 변경 E2E 테스트

최종 보고서에는 테스트 안전 모드 사용 여부, 외부 발송 차단 여부, 결제/환불 외부 호출 차단 여부, DB 변경 테스트 허용 여부를 반드시 포함한다.

## 전체 테스트 실행 전 필수 프리플라이트

`테스트 진행해` 명령을 받으면 실제 테스트를 시작하기 전에 다음을 확인한다.

- 테스트 DB 여부
- TEST_SAFE_MODE=true 여부
- DB_INIT_MODE=safe 여부
- 외부 발송/결제 차단 여부
- scheduler 비활성화 여부
- 업로드 테스트 경로 여부
- ALLOW_E2E_DATA_MUTATION이 테스트 DB에서만 true인지 여부
- TEST_SAFE_MODE=true와 ALLOW_E2E_DATA_MUTATION=true 조합이 코드상 실제로 가능한지 여부

위 조건이 충족되지 않으면 전체 E2E를 실행하지 않고 비파괴 테스트 또는 중단 보고를 수행한다.

프리플라이트 판단 기준:

- 테스트 DB가 확정되지 않으면 DB 쓰기 E2E를 진행하지 않는다.
- 운영 DB 또는 실제 사용자 데이터가 있는 DB 가능성이 있으면 전체 테스트를 중단한다.
- 운영 SMTP/SMS/카카오/FCM/결제 키 사용 가능성이 있으면 전체 테스트를 중단한다.
- `TEST_SAFE_MODE=true`에서는 외부 발송과 결제/환불 호출이 차단되어야 한다.
- `ALLOW_E2E_DATA_MUTATION=true`는 테스트 전용 DB에서만 허용한다.
- 현재 코드는 `TEST_SAFE_MODE=true`와 `ALLOW_E2E_DATA_MUTATION=true`를 분리해서 판정해야 한다. `TEST_SAFE_MODE`는 외부 부작용 차단용이고, `ALLOW_E2E_DATA_MUTATION`은 production이 아니며 DB 이름이 test/e2e/qa 성격일 때만 유효한 DB 쓰기 E2E 허용용이다.
- `allowE2eDataMutation`이 true가 아닌 상태에서는 DB 쓰기 E2E를 실행하지 않는다.
- 테스트 업로드 경로가 운영 업로드 경로와 분리되지 않으면 업로드 E2E를 진행하지 않는다.

### 비파괴 테스트 모드

```text
TEST_SAFE_MODE=true
ALLOW_E2E_DATA_MUTATION=false
```

- DB 쓰기 금지
- 외부 호출 금지
- 스케줄러 금지
- 정적 분석, 빌드, 문법 검사, 비파괴 점검만 가능

### 전체 E2E 테스트 모드

```text
TEST_SAFE_MODE=true
ALLOW_E2E_DATA_MUTATION=true
```

- 테스트 전용 DB에서만 허용
- 외부 발송/결제/스케줄러는 계속 차단
- 회원가입, 예약, 게시글, 영상 등록 등 DB 쓰기 테스트 가능
- 운영 DB에서는 절대 금지
- `allowE2eDataMutation`이 false이거나 테스트 DB가 확정되지 않았으면 실행 전 환경 구성과 재검증이 필요

## 테스트 전용 환경 워크플로우

전체 자동 테스트를 실행하기 전에는 아래 순서를 따른다.

1. `backend/.env.test.example`을 참고해 사용자가 직접 `backend/.env.test`를 만든다.
2. `frontend/.env.test.example`을 참고해 사용자가 직접 `frontend/.env.test`를 만든다.
3. 테스트 DB가 실제 운영 DB와 분리되어 있는지 확인한다.
4. `UPLOAD_ROOT=uploads-test`로 업로드 테스트 경로를 분리한다.
5. 외부 이메일, SMS, 카카오, FCM, 결제, 환불, scheduler allow flag가 모두 `false`인지 확인한다.
6. Playwright base URL은 `PLAYWRIGHT_BASE_URL` 또는 `VITE_E2E_BASE_URL`로 지정한다.
7. 테스트 DB가 확정되기 전에는 `ALLOW_E2E_DATA_MUTATION=true`를 사용하지 않는다.

### Playwright 실행 기준

- Playwright 설정은 서버를 자동 시작하지 않는다.
- 브라우저 E2E는 안전 플래그와 테스트 DB가 확인된 뒤 별도로 실행한다.
- 기본 smoke 테스트는 base URL이 없으면 skip된다.
- 모바일 375px, 태블릿 768px, 데스크톱 Chromium 프로젝트를 기본 검증 대상으로 둔다.

### 전체 E2E 허용 기준

아래 조건을 모두 만족할 때만 `테스트 진행해`에서 DB 쓰기 E2E까지 진행할 수 있다.

- 테스트 전용 DB 확정
- `NODE_ENV=test`
- `TEST_SAFE_MODE=true`
- `DB_INIT_MODE=safe`
- `ALLOW_E2E_DATA_MUTATION=true`
- `UPLOAD_ROOT=uploads-test`
- 외부 발송/결제/환불/scheduler 차단
- 테스트 계정 준비
- 테스트 후 생성 데이터와 업로드 파일 정리 계획 준비

## 환불 스키마 기준

현재 코드 기준 환불 데이터는 단일 `refunds` 테이블을 사용하지 않는다.

- 교육영상/주문 환불 요청은 `refund_requests` 테이블에 저장한다.
- 필라테스 수강권 환불 요청은 `studio_pass_refunds` 테이블에 저장한다.
- `refunds` 테이블이 없다는 이유만으로 프리플라이트를 실패 처리하지 않는다.
- 환불 테스트 커버리지는 `refund_requests`와 `studio_pass_refunds`가 있는지, 각 테이블에 E2E prefix 테스트 데이터가 준비되어 있는지 확인한다.
- 실제 PortOne 결제 조회/환불 호출은 `TEST_SAFE_MODE=true`와 `ALLOW_EXTERNAL_PAYMENT_CALLS=false` 상태에서 항상 차단되어야 한다.

## 환불 E2E seed 기준

- 교육영상 환불 seed는 `refund_requests.id`가 `e2e_` prefix인 데이터만 생성/갱신한다.
- 스튜디오 수강권 환불 seed는 `studio_pass_refunds.id`가 `e2e_` prefix인 데이터만 생성/갱신한다.
- seed는 transaction으로 실행하고 실패 시 rollback한다.
- 운영 DB, 기존 개발 DB, 실제 사용자 데이터에는 환불 seed를 실행하지 않는다.
- 전체 테스트 전에는 환불 seed count를 보고하되 이메일, 전화번호, 비밀번호, 결제키 같은 민감정보는 출력하지 않는다.
