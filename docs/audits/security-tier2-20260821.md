## 2. S-3 — 타인 업로드 파일 삭제

### 2-1. 문제

글 삭제 시 본문의 `/uploads/community/` 경로를 **소유자 확인 없이** unlink 했다. 업로드 파일에는 올린 사람 정보가 남지 않아, 피해자 이미지 경로를 자기 글 `imageUrl` 에 적어 넣고 그 글을 지우는 것만으로 남의 파일을 없앨 수 있었다.

### 2-2. 채택한 우회안 (스키마 변경 없음)

지우기 전에 **후기·문의 글 전체를 훑어 같은 경로를 쓰는 다른 글이 남아 있는지 확인**하고, 참조가 남아 있으면 파일을 그대로 둔다.

```sql
SELECT 1 FROM (
  SELECT image_url, video_url FROM review_posts
  UNION ALL
  SELECT image_url, video_url FROM inquiry_posts
) AS refs
WHERE refs.image_url = ? OR refs.video_url = ?
LIMIT 1
```

삭제(DELETE/UPDATE)가 먼저 일어난 뒤 정리가 호출되므로, **자기 자신의 참조는 이미 사라진 상태**다. 따라서 본인 글의 정상 삭제는 막히지 않는다. 확인 중 오류가 나면 "참조 중"으로 보고 파일을 남긴다 — 잘못 지우는 쪽이 더 위험하기 때문이다.

### 2-3. 이 우회안의 한계

- **피해자 파일이 어느 글에서도 참조되지 않는 상태라면 여전히 지워질 수 있다.** 예: 피해자가 글을 이미 삭제해 파일만 고아로 남은 경우, 또는 업로드만 하고 글을 저장하지 않은 경우
- 참조 검사 대상은 `review_posts` 와 `inquiry_posts` 두 테이블뿐이다. 다른 곳에서 같은 경로를 쓰면 검사에 걸리지 않는다
- 글 수가 늘면 매 삭제마다 전체 스캔이 일어난다. 현재 규모에서는 문제가 없으나 인덱스가 없는 TEXT 컬럼 비교라 대량 데이터에서는 느려질 수 있다
- **근본 해결은 업로드 시 업로더를 기록하는 것**이다(스키마 변경). 승인된 방침에 따라 제안만 남긴다

### 2-4. 검증 (개발 DB 실측)

| 시나리오 | 결과 |
|---|---|
| 공격: 피해자 경로를 넣은 자기 글 삭제 | 피해자 파일 **남음** ✅ |
| 정상: 자기 이미지가 달린 자기 글 삭제 | 파일 **정상 정리** ✅ |
| 마지막 참조(피해자 글) 삭제 | 그때 **삭제됨** ✅ |

## 3. S-9 — 비해당으로 종결

원 지적은 "nginx가 `/uploads/` 를 `alias` 로 직접 서빙해 `app.js` 의 보안 헤더(nosniff·CSP)가 붙지 않는다"였다. 근거는 저장소의 `deploy/nginx-prod.conf` 였다.

**조사 결과 이 판정은 성립하지 않는다.**

- `nginx-prod.conf` 는 배포가 `/etc/nginx/sites-enabled/default` 로 복사하던 파일인데, 그 설정은 `server_name _` 이라 `icl-pilates.com` 요청을 받지 못했다. **실트래픽을 처리하지 않는 죽은 설정**이었다
- 실제 트래픽은 certbot 이 관리하는 `sites-available/icl` 이 처리하며, 이 설정은 `/uploads/` 를 **백엔드로 proxy** 한다. 따라서 요청이 Node 에 도달하고 `app.js:79-95` 의 보안 헤더가 정상적으로 붙는다
- 즉 **취약점은 실재하지 않았고**, 저장소 파일만 보고 판단한 오탐이다

다만 이 조사에서 **더 근본적인 문제**가 드러났다: 저장소가 관리하는 nginx 설정이 실서비스에 반영되지 않는다는 것. 이는 별도 작업으로 처리했다.

→ `chore/nginx-consolidation` 브랜치 `6cbde72`, 문서 `docs/audits/nginx-consolidation-20260821.md`

그 작업에서 `/uploads/` 는 **proxy 를 유지**하도록 명시했다. alias 로 바꾸면 그때 비로소 S-9 이 실재하게 되기 때문이다.

### 과제 2 — `listMembersForAdmin` 페이지네이션

`GET /api/admin/members` 응답이 **2.6MB** 다. 활성 회원 1,133명을 한 번에 반환하며 페이지네이션·검색 파라미터가 없다.

- **성능**: 관리자 화면 진입 때마다 2.6MB 를 내려받고 파싱한다
- **노출 범위**: 한 번의 요청으로 전 회원 데이터가 나간다. 마스킹을 적용해도 이름·수강권·예약 정보는 전량 전달된다
- 권장: 서버 측 페이지네이션과 검색을 도입하고, 화면이 필요한 만큼만 요청하게 한다
